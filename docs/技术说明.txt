-------------------------------------------------
一、为什么先用 Node.js 做渲染，而不是直接开 Gradle 工程
-------------------------------------------------
本机现状（已实测）：
 · Java 17 可用，但 1.21.1 需要 Java 21，环境里没有
 · gradle 命令不存在，只存在 ~/.gradle 缓存目录
 · 无 Python

若直接搭 NeoForge 工程，必须先解决 JDK 21 + Gradle 下载（约 500MB 联网依赖）。
而你这一步的需求只有一件事：**先确认模型造型**。
因此 v0.1.0 采用“零依赖 Node.js 软件渲染器”方案：
 · 造型数据、贴图、渲染器全部可复用
 · 后续生成 Java EntityModel 时直接读同一份 model.js，不会出现两套模型不同步
 · 不需要任何第三方库（PNG 编码、ZIP 打包均自行实现，仅用 Node 内置 zlib）

二、目录结构
-------------------------------------------------

├─ tools\
│  ├─ lib\          基础设施（零依赖）
│  │  ├─ crc32.js   CRC32 查表实现（PNG 与 ZIP 共用）
│  │  ├─ png.js     PNG 编码器（RGBA8，filter 0）
│  │  ├─ zip.js     ZIP 写入器（deflate，UTF-8 文件名位标记）

│  ├─ model\

│  ├─ art\
│  │  ├─ palette.js 调色板 + 稳定哈希噪声
│  │  └─ texture.js 逐面程序化绘制（脸、补子、布料、皮肤）
│  ├─ render\
│  │  ├─ math.js    向量 / 轨道相机 / 透视投影
│  │  ├─ raster.js  z-buffer 光栅化 + 透视校正采样 + Lambert 光照
│  │  ├─ atlas.js   面 → 图集 UV 映射
│  │  ├─ render.js  【入口】多机位渲染 + 拼版
│  │  └─ debug-geo.js 几何调试（每面纯色，用于定位 UV/剔除问题）
│  └─ ops\

├─ docs\            使用说明 / 技术说明 / 经验踩坑

三、坐标系与建模规范
-------------------------------------------------
· 1 单位 = 1 纹理像素，16 单位 = 1 方块（与 Minecraft 一致）
· y 轴向上，原点在双脚中心地面，+Z 为模型正前方，+X 为模型自身左侧
· 每个盒子 = { id, part, min, max, mat, xform }
· xform = { pivot, rot:[rx,ry,rz] } 用于把整组盒子围绕关节旋转
  —— 手臂就是靠这个机制一次性前伸 84°，而不是分别旋转上臂/小臂

模型尺寸：
  总高 44.3 单位（含顶珠），肩宽 18.2，含前伸手臂总深约 19 单位。
  对应游戏内约 2.76 格高、1.14 格宽（僵尸原版 1.95 格高），
  该比例是为了容纳官帽与长袍，实际实体会额外做 0.9 缩放。

-------------------------------------------------
四、渲染管线
-------------------------------------------------
1. buildBoxes()    → 39 个盒子
2. facesOf()       → 234 个面（每面记录 4 角点 + 世界法线 + 面尺寸）
3. packFaces()     → 每个面独立矩形，打包进 128×128 图集
                      （step 4 的每个面都有独立 UV，天然零重叠）
4. paintAtlas()    → 按 box id + 面朝向分派绘制函数，输出 512×512
                      （scale=4 放大，避免预览时纹理过软）
5. renderFrame()   → 相机变换 → 背面剔除 → 由远到近排序 → 三角形光栅化
                      含 1/z 插值的透视正确 UV、z-buffer、Lambert + 环境光

光照：方向光 (0.62,-0.55,0.85) 归一化，ambient 0.52，diffuse 0.62，
      侧面额外 ×0.94、顶底面 ×1.02，用于强化方块体积感。

-------------------------------------------------
五、贴图策略
-------------------------------------------------
采用“每面独立矩形”而非 Minecraft 原生的 body 展开式 UV。
原因：
 · 任意尺寸的盒子都能安全映射，不需要为每个盒子手算 6 个偏移
 · 零重叠、零缝隙，预览阶段不会出现纹理串色
后续生成 Java 模型时，会再提供一份导出器，把同一批面写成
原生展开式 UV（这样游戏内的贴图可以只占 64×64），两份 UV 都由
atlas.js 统一推导，避免手工维护。
